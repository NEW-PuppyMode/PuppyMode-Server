## 1.1 무엇을 알고 싶었나
"n8n이 느려지거나 신고가 몰려도, **신고자 쪽은 안전한가? 운영자 알림은 얼마나 가는가?**"

신고 접수는 DB 커밋 후 응답하고, 알림은 `AFTER_COMMIT` 이후 별도 풀에서 비동기로 보낸다. 알림 풀은 core 1 / max 2 / queue 20이고, 가득 차면 경고 로그 한 줄만 남기고 알림을 버린다. 웹훅 전송 타임아웃은 5초다. [확인]

## 1.5 핵심 발견

**① 신고는 안전하고, 유실되는 건 운영자 알림이다.**
신고는 커밋 후 응답하므로 4,405건 모두 DB에 저장됐다. 폐기되는 것은 "새 신고가 왔다"는 알림뿐이다.

**② 알림 풀의 처리 용량이 산식으로 예측된다.**
처음 받아 줄 수 있는 양(running 2 + queue 20 = 22)에, 웹훅 응답 시간 L 동안 스레드 2개가 비워 주는 슬롯이 더해진다.

`수용 건수 ≈ 22 + (2 ÷ L) × 지속시간`

| 시나리오 | 예측 | 실측 |
|---|---|---|
| S1 (L=4s, 30s) | 22 + 0.5×30 = 37 | 35 / 36 / 36 |
| S2 (L=4s, 20s) | 22 + 0.5×20 = 32 | 30 / 30 |
| S1t (스레드 5초 점유, 20s) | 22 + 0.4×20 = 30 | 28 |

실측이 1~2건 적다(스레드 기동·종료 시점). 이 산식으로 개선안의 효과를 사전에 계산할 수 있다.

**③ 처리량 상한이 `2 ÷ L`로 매우 낮다.**
L=4초에서 0.5건/초뿐이라, 초당 10건의 **평범한 부하에서도 88%가 폐기**된다.

**④ 폐기 메트릭을 추가해 검증했다.**
`notification_dropped_total{name="complaintExecutor"}`를 추가하고, 평소(101건) 0 = 0, 폭주(1,001건) **971 = 971**로 로그와 일치함을 확인했다. 폐기 0건일 때도 지표가 0으로 노출된다.

# Part 2. 성능 개선 설계

## 2.1 병목 진단

```
신고 접수 → [큐 20] → 스레드 2개 → .block(5초)  → n8n/Slack
                         ↑ 응답을 기다리는 동안 스레드를 붙잡음
```

- 알림 한 건이 스레드 1개를 **웹훅 응답 시간 L 동안** 점유한다.
- 처리량 상한 = `스레드 수 ÷ L` = `2 ÷ L`. 이것이 [실측]으로 확인된 병목이다(§1.5-②).
- 리틀의 법칙: 동시에 처리 중인 알림 수 = `도착률 λ × L`. 이 값이 스레드 수(2)를 넘으면 큐가 차고, 큐도 넘으면 폐기된다.

**핵심 통찰**: 알림 전송은 CPU 작업이 아니라 **네트워크 대기**다. 대기하는 동안 스레드를 점유할 이유가 없다. 처리량이 모자란 이유는 "일꾼이 적어서"가 아니라 "일꾼이 기다리느라 못 쓰여서"다.

## 2.2 개선안 후보와 효과 예측

효과는 S1(초당 10건 × 30초 = 300건, L=4초)과 S2(초당 50건 × 20초 = 1,000건, L=4초) 기준 **[예측]**이다.

| 후보 | S1 도달률 | S2 도달률 | 비용 | 리스크/한계 | 판단 |
|---|---|---|---|---|---|
| V0 현재 | 11.9% [실측] | 3.0% [실측] | - | - | 기준선 |
| **타임아웃 단축** (5→2초) | 의미 없음 | 의미 없음 | 상수 → 설정화 | **L(4초) > 타임아웃이면 전부 실패.** 폐기는 줄지만 도달은 0 | 단독으로는 부적합. 응답이 타임아웃 안에 오는 환경에서만 보조 수단 |
| **스레드·큐 확대** (예: 50스레드, 큐 200) | 100% (수용 250 + 12.5×30 ≥ 300) | 약 50% (수용 250 + 12.5×20 = 500) | 설정만 | 스레드 50개 상주(블로킹 대기용), 처리량이 여전히 `스레드÷L`에 묶여 S2처럼 몰리면 손실 | 단기 완화책일 뿐 근본 원인(블로킹)을 안 고침 |
| **비차단 전송 + 동시성 상한 C** | **100%** (C≥50) | C=250이면 **100%**, C=100이면 60% | 중간 (전송부 재작성, 풀 설정, 테스트) | 하류 부하가 그대로 전달됨(n8n/Slack 한도) | **가장 효과가 큼. Phase A로 채택** |
| **알림 합치기(digest)** | 100% | 100% | 중간 (n8n 워크플로 변경 필요) | 지연 증가(합치는 시간만큼), 한 번 실패하면 N건이 같이 사라짐 | 하류 보호용. Phase B |
| **outbox + 재시도 워커** | 100% (지연 후 도달) | 100% (지연 후 도달) | 큼 (테이블·워커·멱등성) | 신고 API에 INSERT 추가, 중복 전송(at-least-once) | 내구성용. Phase C |

### 산식과 근거 [예측]
- 비차단(상한 C, 대기열 없음): `수용 ≈ C + (C ÷ L) × 지속시간`
  - 손실이 없으려면 **`C ≥ 도착률 × L × 여유`** (리틀의 법칙)
  - S1: 10 × 4 = 40 → C=60이면 충분
  - S2: 50 × 4 = **200** → C=250이면 여유 있음

| 상한 C | S2 수용 건수 (1,000건 중) | 도달률 | 폐기율 |
|---|---|---|---|
| 20 (WebClient 기본 풀) | 20 + 5×20 = 120 | 12% | 88% |
| 50 | 50 + 12.5×20 = 300 | 30% | 70% |
| 100 | 100 + 25×20 = 600 | 60% | 40% |
| 200 | 200 + 50×20 = 1,200 ≥ 1,000 | 100% | 0% |
| 250 (권장) | 250 + 62.5×20 ≥ 1,000 | 100% | 0% |

- 현재 방식은 같은 시나리오에서 3.0% (실측). **같은 L이라도 스레드를 점유하지 않으면 한계가 `2÷L`에서 `C÷L`로 올라간다.**
- 스레드 확대가 비효율인 이유: 스레드 50개로 올려도 `50÷4 = 12.5건/초`이면서 스레드 50개가 **잠만 자는 상태**다. 비차단은 같은 동시성을 스레드 없이 얻는다.

### 실제 웹훅이 빠르다면? (민감도) [예측]
n8n 응답이 빠르면 현재 구조도 꽤 버틴다. 그래서 L을 모르는 것이 중요하다.

| L (웹훅 응답) | 현재 처리량 상한 `2÷L` | 비차단 C=100 `100÷L` | 초당 10건 × 30초에서 현재 폐기율 |
|---|---|---|---|
| 0.3초 | 6.7건/초 | 333건/초 | 약 26% (수용 22 + 6.7×30 ≈ 222 / 300) |
| 1초 | 2건/초 | 100건/초 | 약 73% (수용 22 + 2×30 = 82 / 300) |
| 4초 | 0.5건/초 | 25건/초 | 88% [실측] |

- 신고가 초당 10건씩 30초 지속되는 상황은 이 서비스에서 **현실적이지 않을 가능성이 높다**(신고는 드문 이벤트). 실제 평소 부하에서는 폐기가 없을 수 있다.
- 따라서 개선의 가치는 "평소 처리량"이 아니라 **n8n이 일시적으로 느려졌을 때(L이 평소의 10배 이상)와 신고가 몰릴 때의 여유**다. 이 여유를 얼마나 둘지는 실제 L과 신고량이 정한다.

## 2.3 추천안: 단계별 도입

```
Phase 0  관측 보강          (먼저, 동작 변경 없음)
Phase A  비차단 전송 + 상한  (핵심 개선, 가장 효과 큼)
Phase B  알림 합치기        (하류 보호, 필요 시)
Phase C  outbox + 재시도     (내구성 필요 시)
```

### Phase 0. 실제 웹훅 응답시간 측정 (동작 변경 없음)
모델의 핵심 입력 L을 모른 채 C를 정할 수 없다.
- `notification.send` 타이머 추가: 태그 `result = success | http_error | timeout | error`, 메트릭은 `notification_send_seconds`(히스토그램 포함)로 노출
- `notification.inflight` 게이지(Phase A에서 의미가 생김)
- 개발 서버에서 실제 신고 알림을 몇 번 보내거나, 현재 코드에 타이머만 먼저 넣어 L의 p50/p95/p99를 얻는다
- **이 값으로 C와 타임아웃을 정한다.**

### Phase A. 비차단 전송 + 명시적 동시성 상한 (핵심)

**목표**: 스레드를 붙잡지 않고, 동시 전송 수를 **명시적으로** 제한한다.

#### 구조
```java
public void send(String text, Map<String, ?> data) {
    if (urlBlank) { warn; return; }
    if (!inFlight.tryAcquire()) {                   // 상한 C 초과 → 폐기
        droppedCounter(reason="inflight_limit").increment();
        log.warn("[신고 Slack 알림] 동시 전송 상한을 넘어 알림을 건너뜁니다.");
        return;
    }
    webClient.post()...bodyValue(...)
        .retrieve().toBodilessEntity()
        .timeout(timeout)                           // block 타임아웃 대신
        .doFinally(sig -> inFlight.release())       // 성공/실패/취소 모두 반납
        .subscribe(
            ok -> record(success),
            err -> logFailure(err));                // 기존과 동일: HTTP 코드/예외 종류만
}
```

#### 설계 결정
| 결정 | 선택 | 이유 |
|---|---|---|
| 동시성 제한 방식 | `Semaphore`(명시적 상한) | WebClient 커넥션 풀 대기열에 맡기면 **기본값이 최대 20, 대기 45초**라 의도와 다르게 동작([확인], 이 PC 기준 `DEFAULT_POOL_MAX_CONNECTIONS=20`, `ACQUIRE_TIMEOUT=45000ms`). 상한과 폐기를 코드에서 직접 통제하고 메트릭으로 센다 |
| 커넥션 풀 크기 | `ConnectionProvider`의 maxConnections를 C 이상으로 설정 | 기본 20개면 C를 올려도 풀에서 막힌다. **세마포어 C와 커넥션 풀을 맞춘다** |
| 초과 시 | 폐기 + 카운터(`reason=inflight_limit`) | 기존 "알림은 버려도 신고는 안전" 원칙 유지. 큐를 무한히 늘리지 않음 |
| 타임아웃 | `Mono.timeout` + `HttpClient.responseTimeout`, 설정 키로 분리 | 이제 타임아웃은 스레드가 아니라 **in-flight 슬롯**을 붙잡는 시간이다. `in-flight = λ × min(L, 타임아웃)` |
| 실패 로그 | 기존 규칙 유지 | URL·시크릿·예외 메시지는 로그에 남기지 않음(HTTP 코드/예외 종류만) |
| 재시도 | **넣지 않는다** | 단순 재시도는 느린 하류에 부하를 더하는 재시도 폭풍을 만든다. 재시도는 Phase C에서 백오프와 함께 |
| 리스너·풀 | 유지 | `@Async` 풀 작업이 마이크로초에 끝나 풀 포화(22건)가 사실상 사라진다. 코드 변경 최소화 |

#### 설정 키 (제안)
| 키 | 기본값 | 설명 |
|---|---|---|
| `complaint.slack.send-mode` | `blocking` → 검증 후 `async` | 롤아웃·A/B 측정용 스위치. 안정화되면 제거 |
| `complaint.slack.max-in-flight` | 250 (Phase 0의 L로 조정) | 동시 전송 상한 C |
| `complaint.slack.timeout-ms` | 5000 | 응답 타임아웃 |
| `complaint.slack.connect-timeout-ms` | 2000 | 연결 타임아웃 |

#### 관측 (새 메트릭)
- `notification_dropped_total{name, reason}`: 기존 카운터에 `reason` 태그(`queue_full` / `inflight_limit`) 추가
- `notification_inflight`: 현재 동시 전송 수 → 포화 직전 징후
- `notification_send_seconds{result}`: 응답시간 분포(Phase 0에서 도입)
- 알람 예(미적용): `notification_inflight / max_in_flight > 0.8`가 지속, `increase(notification_dropped_total[5m]) > 0`

#### 테스트 계획
**단위** (`ExchangeFunction`에 지연 응답을 주는 가짜 WebClient)
1. 응답이 4초 걸려도 `send()`는 **즉시 반환**한다(수십 ms 이내)
2. `max-in-flight=C`일 때 동시에 N건을 보내면 **C건만 전송되고 나머지는 폐기 + 카운터**
3. 성공·HTTP 오류·타임아웃·예외 **모두 슬롯을 반납**한다(누수 없음: 오류 후에도 다시 C건 수용)
4. 로그에 URL·시크릿·예외 메시지가 없다(기존 회귀 테스트 이식)
5. `send-mode=blocking`일 때 기존 동작과 동일

**부하** (같은 도구, 같은 시나리오, 앱만 `--complaint.slack.send-mode=async` 등으로 전환)

#### 합격 기준 [예측을 기준으로 정함]
| 시나리오 | 현재(실측) | 목표 | 근거 |
|---|---|---|---|
| S1 (10/s, L=4s) | 도달 11.9% | **도달 100%, 폐기 0** | in-flight 피크 ≈ 40 ≤ C |
| S2 (50/s, L=4s), C=250 | 도달 3.0% | **도달 100%, 폐기 0** | in-flight 피크 ≈ 200 ≤ 250 |
| S2, C=100 | - | 도달 약 60% (산식 검증) | `C + (C÷L)×D` 맞는지 확인 |
| 신고 API p95 | 16~25ms | 기준선 대비 +10% 이내 | 알림 경로가 신고 경로에 영향을 주면 안 됨 |
| S3·S4 (500/403) | 로그 노출 0 | 그대로 0 | 로그 안전성 회귀 방지 |
| 슬롯 누수 | - | 오류 후에도 `inflight` 게이지가 0으로 복귀 | 반납 누락 방지 |

### Phase B. 알림 합치기 (digest) — 하류 보호

**왜 필요한가**: 비차단으로 바꾸면 **하류로 가는 요청이 그대로 늘어난다.** 이 서비스의 하류에는 제약이 있다.
- n8n Cloud 무료 체험은 **월 1,000회 실행 한도**다. 신고 1,000건이 몰리면 20초 만에 한 달 치를 소진한다.
- Slack 채널 게시에는 초당 요청 한도가 있다(정확한 현재 값은 Slack 공식 문서에서 확인 필요).

**방식 (leading + trailing)**: 신고 한 건이 처음 오면 즉시 보내고(낮은 지연), 이후 창(window, 예: 5초) 동안 오는 건 메모리에 모았다가 창이 끝날 때 한 번에 보낸다. 본문은 `text`(요약: "신고 N건 접수, 사유별 …")와 `items[]`(건별 구조화 필드)를 같이 보낸다.

**효과 [예측]**: 초당 50건 × 20초 = 1,000건 → 첫 건 1회 + 이후 창마다 1회 = 약 **5회** 호출. 하류 호출이 약 200분의 1로 줄어 **n8n 실행 한도도 보호**된다.

**비용·리스크**
- n8n 워크플로 변경: Webhook 뒤에 `items[]`를 건별로 펼치는 노드(Split Out 등)를 두어야 Sheets에 건별 행이 쌓인다.
- 지연 증가(창 길이만큼). 한 번의 호출이 실패하면 N건이 같이 사라지므로, **Phase C(재시도)와 함께일 때 가치가 큼.**
- 합치는 버퍼는 메모리라 서버가 죽으면 최대 창 길이만큼 손실된다.

### Phase C. outbox + 재시도 — 내구성
- 신고 저장과 **같은 트랜잭션에서 outbox 행을 기록**하고, 워커가 읽어 전송·재시도(지수 백오프 + 지터, 최대 횟수, 실패 시 DLQ 상태)한다.
- 효과: n8n이 몇 시간 죽어 있어도, 서버가 재시작돼도 **알림을 잃지 않는다.** "폐기"가 "지연"으로 바뀐다.
- 비용: 테이블·워커·멱등성(`complaintId` 기준 중복 제거) 설계, 신고 API에 INSERT 1건 추가(p95 영향 측정 필요), 중복 전송 허용(at-least-once).
- Phase A·B로 목적(폭주·지연 대응)을 달성했다면 **내구성 요구가 확정될 때까지 보류**해도 된다. 이미 `UserComplaint` 테이블이 신고 원본이므로, outbox가 없어도 운영자가 DB에서 누락 신고를 조회할 수 있다.

## 2.4 하지 않을 것과 이유
| 하지 않을 것 | 이유 |
|---|---|
| 스레드 풀만 키우기 | 블로킹 대기용 스레드를 수십 개 상주시키는 낭비. 처리량 상한이 여전히 `스레드÷L` |
| 큐 무제한 | 메모리 고갈 위험, 지연이 무한정 길어짐 |
| `CallerRunsPolicy`(요청 스레드가 직접 전송) | 신고 응답이 웹훅 지연에 묶여 **이번 측정에서 증명한 격리가 깨짐** |
| 타임아웃만 단축 | L이 타임아웃보다 길면 전부 실패 |
| Phase A에서 재시도 추가 | 느린 하류에 재시도 폭풍. 재시도는 백오프·상한과 함께 Phase C에서 |
| 처음부터 outbox | 효과 대비 비용이 가장 큼. A로 해결되는 문제를 C로 풀 필요 없음 |

## 2.5 검증 계획 (같은 부하, 변형 하나씩)

| 단계 | 내용 | 산출물 |
|---|---|---|
| 0 | Phase 0 구현·배포 → 개발 환경에서 L(p50/p95/p99) 확보 | 실제 L, C·타임아웃 산정 근거 |
| 1 | 가짜 웹훅에 **지연 분포**(예: 평소 300ms + 5%는 4초)와 `complaintId` 중복 집계 추가. 러너에 `--label`, 도달률·실패율 지표 추가 | 도구 보강 |
| 2 | Phase A 구현 + 단위 테스트 | 코드, 테스트 |
| 3 | 매트릭스 측정: `send-mode ∈ {blocking, async}` × 시나리오(S0, S1, S2, S3, S4, 지연 분포) × **교차 3회**, 워밍업 폐기 | 비교 리포트 |
| 4 | 판정(§2.2 합격 기준 대비), 산식 [예측] vs [실측] 대조 | 리포트, 포트폴리오 수치 갱신 |

**지표 재정의**: 폐기율만 보면 타임아웃 단축처럼 "폐기는 줄지만 실패가 늘어나는" 변화를 놓친다. **도달률(웹훅이 200으로 응답한 건수 ÷ 신고 건수)**을 핵심 지표로, 폐기율·실패율·신고 API p95를 보조 지표로 쓴다.

## 2.6 리스크 정리
| 리스크 | 대응 |
|---|---|
| 모델의 입력 L을 모른다 | Phase 0에서 실측 후 C 결정 |
| 동시성 C를 크게 잡아 하류(n8n)를 압박 | C를 설정화, in-flight 게이지·알람, Phase B 병행 검토 |
| 커넥션 풀 기본값(20)이 C를 가로막음 | `ConnectionProvider` 설정을 C와 함께 변경, 부하 테스트로 확인 |
| 비차단 전환 중 슬롯 누수 | `doFinally`로 반납, 오류 후 복귀 단위 테스트 |
| 로그에 URL·시크릿 노출 회귀 | 기존 회귀 테스트 이식 + 부하 테스트의 로그 검사 |
| 서버 종료 시 in-flight 알림 손실 | 허용(알림은 부가 기능). 내구성이 필요하면 Phase C |
| 로컬 측정을 운영 성능으로 오해 | 문서·리포트에 환경과 조건을 항상 명시 |

## 2.7 결정이 필요한 것
1. **Phase 0부터 시작**해 실제 L을 먼저 잴지, 바로 Phase A를 구현할지. (저는 Phase 0을 권한다. 가장 작고, 이후 모든 결정의 입력이다.)
2. **동시성 상한 기본값**: 실제 L을 알기 전까지 임시로 250을 쓸지.
3. Phase B(합치기)는 **n8n 워크플로 변경**이 필요하다. 시트에 건별 행이 쌓이는 현재 구조를 바꿔도 되는지.
4. 실제 평소 신고량과 n8n 응답시간(n8n Executions 화면의 실행 시간으로 대략 확인 가능)을 알려 주면 목표 수준을 더 정확히 잡을 수 있다.
